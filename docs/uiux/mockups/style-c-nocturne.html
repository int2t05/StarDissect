ripgrep：面向开发者的并行文本搜索设计

一个问题驱动的设计解剖：为什么"快"来自边界划分而不是线程数。

仓库 BurntSushi/ripgrep 类型 CLI / 开发工具 固定于 commit 14.1.0 分析 2026-10-01 预计 18 分钟

学习看点

并行边界为什么划在"目录遍历"而不是"文件读取"；字面量优化器如何把正则搜索降级为字节扫描；CLI 体验被当作架构需求对待的具体做法。

01 · 需求与约束

ripgrep 的目标是替代 grep 的日常使用而非全部场景：默认递归、尊重 ignore 规则、输出面向人。工具被成千上万次调用，单次启动延迟比吞吐更显性——这一约束决定了后面的每个取舍。

02 · 核心决策：并行边界的位置

遍历目录产生的"待搜文件"被送入有界队列，固定数量的工作线程消费并执行搜索。并行单位是文件，不是行。文件边界天然独立，且与 ignore 规则的判定主体一致。

源码事实
目录遍历器与工作线程之间通过有界通道衔接；遍历线程生产路径，worker 池消费并搜索。生产者不做搜索，消费者不做遍历。
crates/ignore/src/walk.rs · commit 14.1.0 ↗
分析推断
分析推断：选择文件级并行的另一半原因是有界队列天然提供背压，避免目录爆炸时内存失控。作者未在文档中明确说明此动机。

03 · 字面量优化：正则的降级路径

当模式可判定为"只匹配字面量"时，引擎退化为 memchr 式查找。最常见用例从"有限自动机"降为"字节扫描"，启动延迟与吞吐同时受益。
